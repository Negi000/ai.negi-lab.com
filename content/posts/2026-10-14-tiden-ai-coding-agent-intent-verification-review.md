## 結論から: このツールは「買い」か

結論から言うと、エージェントに「自律的なリファクタリング」を任せたいチームにとって、Tidenは非常に価値のある投資になります。
評価としては星4つ（★★★★☆）です。
既存のClineやAiderといったツールは強力ですが、一歩間違えるとプロジェクト全体を破壊するリスクを孕んでいます。
Tidenはその「最後の一線」を、ルールベースとLLMによる検証のハイブリッドで守ってくれます。

一方で、AIに指示を出してその場で結果を確認するだけの「対話型開発」をしている人には不要です。
わざわざ検証ロジックを組む手間が、開発スピードを落としてしまうからです。
「バックグラウンドでエージェントを走らせておき、承認された変更だけを反映したい」という実務重視のエンジニアには、これ以上ない武器になるはずです。

## このツールが解決する問題

これまでのコーディングエージェントの最大の問題は、指示の「解釈のズレ」が致命的な破壊行動につながることでした。
例えば「古い関数を削除して」と指示した際、エージェントが依存関係を無視して広範囲にファイルを消し去るようなケースです。
従来はこれを防ぐために、人間がエージェントのアウトプットを一行ずつレビューする「Human-in-the-loop」が不可欠でした。
しかし、これではエンジニアのリソースが奪われ、自動化のメリットが半減してしまいます。

Tidenは、エージェントが実際にコードを書き換える前に「インテント（意図）の検証」というフェーズを強制的に挿入します。
具体的には、エージェントが提案した「アクションプラン」を読み取り、それが定義された制約条件に違反していないかをチェックします。
「特定のディレクトリ外のファイルは触らない」「テストコードを削除してはいけない」といったガードレールを動的に適用できるのが強みです。
これにより、エンジニアは「AIが何をするか」を監視する作業から解放され、「AIが何をすべきか」という定義に集中できるようになります。

## 実際の使い方

### インストール

TidenはPython環境で動作するライブラリとして提供されています。
検証用のLLMモデル（GPT-4oやClaude 3.5 Sonnetなど）を別途用意する必要があります。

```bash
pip install tiden-sdk
```

動作環境としてはPython 3.10以降が推奨されています。
また、ローカルで検証モデルを動かしたい場合は、VRAM 16GB以上のGPU（RTX 4060 Ti 16GB等）があると、推論コストを抑えつつ高速に検証を回せます。

### 基本的な使用例

Tidenの核心は、エージェントの出力を「検証（Verify）」するプロセスにあります。
以下は、エージェントが提案したファイル削除のプランを検証する基本的な流れです。

```python
from tiden import IntentVerifier, Policy
from tiden.models import ActionPlan

# 1. ポリシー（制約）の定義
# ここでは「テストファイル（test_で始まるファイル）の削除は禁止」というルールを設定
policy = Policy(
    allow_file_modification=True,
    protected_paths=["**/tests/**", "**/test_*.py"],
    require_test_coverage=True
)

# 2. 検証エンジンの初期化
verifier = IntentVerifier(api_key="sk-...", policy=policy)

# 3. エージェントが生成したプラン（シミュレーション）
proposed_plan = ActionPlan(
    actions=[
        {"type": "delete", "path": "src/utils.py", "reason": "Unused code"},
        {"type": "delete", "path": "tests/test_utils.py", "reason": "Corresponding test"}
    ],
    original_intent="不要なユーティリティ関数の削除"
)

# 4. 検証の実行
report = verifier.verify(proposed_plan)

if report.is_valid:
    print("実行を許可します")
else:
    print(f"却下されました: {report.rejection_reason}")
    # tests/test_utils.py の削除がポリシー違反として検出される
```

実務では、この`verifier.verify()`をエージェントのメインループの直後に配置します。
検証結果が`False`の場合は、エージェントにフィードバックを返し、プランを再生成させるという運用が一般的です。

### 応用: 実務で使うなら

実際の開発現場では、TidenをCI/CDパイプラインや、Gitのプリコミットフックのような形で組み込むのが最も効果的です。
例えば、開発者がGitHubのIssueに「〇〇の機能を修正して」とコメントした際、裏側でエージェントが走り出します。
Tidenはそのエージェントが作ったPR（プルリクエスト）の内容をスキャンし、「セキュリティ的に脆弱なコードが含まれていないか」「意図しない設定ファイルの変更がないか」を事前にレポートします。

特に、大規模なモノレポ（Monorepo）環境では、エージェントが触っていい範囲を限定することが極めて重要です。
Tidenのディレクトリベースの権限管理を使えば、「決済関連のディレクトリ（/payments）は、人間が明示的に許可した時以外は変更不可」といった運用がコードベースで記述できます。
これは、複数のAIエージェントを同時に走らせるマルチエージェント環境において、システムの整合性を保つための「交通整理役」として機能します。

## 強みと弱み

**強み:**
- エージェントの「思考プロセス」と「実行結果」を分離して評価できるため、透明性が高い
- 既存のLangChainやLlamaIndexといったフレームワークと組み合わせて使いやすいシンプルなAPI設計
- ユーザーの意図（Natural Language Intent）を構造化データに変換し、決定論的なルール（Pythonコード）と比較できる
- 検証ロジック自体をGit管理できるため、チーム内での合意形成がしやすい

**弱み:**
- 検証用にもLLMを使用する場合、トークンコストとレスポンス時間が二重にかかる
- 「意図」の定義が曖昧だと、検証側も誤判定（False Positive/Negative）を起こす可能性がある
- 現時点ではドキュメントが英語のみであり、日本語のニュアンスを含む複雑な指示の検証には工夫が必要
- 大規模なプラン（100ファイル以上の変更など）の検証には、コンテキストウィンドウの広いモデルが必須になる

## 代替ツールとの比較

| 項目 | Tiden | Guardrails AI | LangGraph (H-i-t-l) |
|------|-------------|-------|-------|
| 主な用途 | エージェントの意図検証 | 出力形式のバリデーション | 人間による承認フロー |
| 検証手法 | インテント・マッチング | Pydantic/スキーマ定義 | マニュアル承認 |
| 導入コスト | 低（SDK導入のみ） | 中（スキーマ定義が必要） | 高（グラフ構造の構築） |
| 特徴 | コーディングに特化 | 汎用的な出力制御 | 確実だが時間がかかる |

結論として、柔軟な「意図」を扱いたいならTiden、決まった「データ形式」を守らせたいならGuardrails AI、絶対にミスが許されないミッションクリティカルな環境ならLangGraphでの人間介入を選ぶべきです。

## よくある質問

### Q1: 検証に使うモデルは、メインのエージェントと同じで良いですか？

理想は、メインより「賢い」または「別系統」のモデルを使うことです。
同じモデルを使うと、同じ論理的ミスを繰り返すリスクがあります。
メインがGPT-4oなら、検証はClaude 3.5 Sonnetに任せるなど、モデルの多様性を確保するのが実務上のコツです。

### Q2: 実行速度（レイテンシ）への影響はどの程度ですか？

プランの規模によりますが、10ファイル程度の変更プランであれば、GPT-4o-mini等を使えば0.5秒〜1.5秒程度で検証が完了します。
この時間は、人間がレビューする数分間に比べれば無視できるレベルです。

### Q3: 既存のテスト（Pytest等）があればTidenは不要ですか？

テストは「コードが正しく動くか」を確認しますが、Tidenは「指示通りの場所を、指示通りの意図で触っているか」を確認します。
例えば「テストは通るが、実は触ってはいけない基幹ライブラリを強引に書き換えていた」といった事態は、Tidenでないと防げません。
